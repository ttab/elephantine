# Migrating from v0.29 to v0.30

Two changes need work at a call site: the task and job supervision APIs took a
breaking change, and a service that raised the API server's request body limit
for the sake of a Connect request has to move that number to a new option.
Everything else in the release is additive.

## `ErrGroup.GoWithRetries` and `joblock.Options`

`GoWithRetries` takes a `RetryOptions` struct, its failure budget is a
duration rather than a count, and the backoff curve is the library's own:
`BackoffFunction` and `StaticBackoff` are gone, with nothing to replace them.
`joblock.Options` takes the same five fields, so both supervision APIs read
the same way.

| Before | Now |
| -- | -- |
| `GoWithRetries(task, maxRetries, backoff, resetAfter, fn)` | `GoWithRetries(task, RetryOptions{…}, fn)` |
| `maxRetries int` | `GiveUpAfter time.Duration` — how long it may go on failing |
| `resetAfter time.Duration` | `HealthyRuntime time.Duration` — how long a run must last to clear the budget |
| `backoff BackoffFunction` | `BackoffFloor` / `BackoffCeil`, an exponential curve with jitter |
| `StaticBackoff(d)` | removed; the curve is not caller-supplied |
| `joblock.Options.MaxConsecutiveFailures int` | `joblock.Options.GiveUpAfter time.Duration` |
| — | `MinRuntime time.Duration`, the minimum interval between two starts |

`GoWithRetries` picks up the pacing `joblock.Run` already had, so a task is
restarted at most once per `MinRuntime` — ten seconds by default. A call site
that retried every second under `StaticBackoff(time.Second)` now waits ten,
unless it lowers `MinRuntime` along with `BackoffFloor`.

Nothing else about the two loops changed: a task that returns nil is still
done, a `joblock.Run` function is still restarted whether it returned an error
or not, a panic is still recovered and counted as a failure, and a
`joblock.Run` cut short by the loss of the lock still counts as neither.

### Picking `GiveUpAfter`

**The budget is wall-clock time since the first failure of the current
streak**, and the waits between restarts count towards it. The question it
answers is *how long do we allow this to stay broken*, which is the question
the call sites were already answering in a comment above the old count.

So the conversion is not arithmetic: take the duration the call site says it
wants and write that down. If there is no such comment, the table below is
what the old count bought under the current curve, for a task that fails
instantly.

| Consecutive fast failures | Elapsed under the default curve |
| -- | -- |
| 5 | ~40 seconds |
| 10 | ~3½ minutes |
| 20 | ~11 minutes |
| 30 | ~18 minutes |

The curve flattens at the ceiling, so past ten failures each further one is
worth about 45 seconds. A budget carried across from a count therefore means a
different amount of time than the count did under a static backoff — that is
the point of the change, and it is why a recomputed count would have been less
faithful than the durations the call sites already documented.

Zero still means "never give up", and is still the default.

### Worked examples

A supervisor that gave up after a while:

```go
// Before: bail after approximately 5 minutes of retries.
eg.GoWithRetries("archive", 30,
	elephantine.StaticBackoff(10*time.Second), time.Hour, run)

// After.
eg.GoWithRetries("archive", elephantine.RetryOptions{
	GiveUpAfter:    5 * time.Minute,
	HealthyRuntime: time.Hour,
}, run)
```

The comment goes with the constant: the duration is the documentation now.

A supervisor that restarts forever:

```go
// Before.
eg.GoWithRetries("subscriber", 0,
	elephantine.StaticBackoff(5*time.Second), time.Hour, run)

// After. GiveUpAfter is zero, so it could be left out; naming it says the
// unbounded restart was a decision.
eg.GoWithRetries("subscriber", elephantine.RetryOptions{
	GiveUpAfter:    0,
	HealthyRuntime: time.Hour,
}, run)
```

A supervisor that took every default:

```go
// Before, with taskRetryReset = 5 * time.Minute.
eg.GoWithRetries(name, 10,
	elephantine.StaticBackoff(5*time.Second), taskRetryReset, fn)

// After. Five minutes is DefaultHealthyRuntime, so the constant can go.
eg.GoWithRetries(name, elephantine.RetryOptions{
	GiveUpAfter: time.Minute,
}, fn)
```

A job lock:

```go
// Before, with maxJobLockFailures = 30 ("on the order of fifteen to twenty
// minutes").
joblock.Run(ctx, db, logger, "renderer", "renderer", joblock.Options{
	MetricsRegisterer:      reg,
	MaxConsecutiveFailures: maxJobLockFailures,
}, run)

// After.
joblock.Run(ctx, db, logger, "renderer", "renderer", joblock.Options{
	MetricsRegisterer: reg,
	GiveUpAfter:       20 * time.Minute,
}, run)
```

### `BackoffFloor` below `MinRuntime` does nothing

A restart is padded out to `MinRuntime` — ten seconds by default — so the
backoff is invisible until it has doubled past that, somewhere around the
fifth or sixth failure. **A call site that wants a faster first retry has to
lower `MinRuntime` too**, which is why that field is configurable rather than
an internal constant. The pair is also what lets a test drive the curve in
milliseconds now that it cannot supply one:

```go
grp.GoWithRetries("flaky", elephantine.RetryOptions{
	BackoffFloor: time.Millisecond,
	BackoffCeil:  2 * time.Millisecond,
	MinRuntime:   time.Millisecond,
}, fn)
```

### Why the budget stopped being a count

`GoWithRetries` reset its retry counter when more than `resetAfter` had passed
since the last failure — but it stamped that clock *before* the backoff sleep,
so the interval it measured was the wait plus the runtime rather than the
runtime of the run that failed. With a constant backoff well under
`resetAfter` that was invisible. Under an exponential curve every wait past
`resetAfter` would have reset the counter on the strength of its own sleep,
however fast the task failed, making `maxRetries` unreachable and the limit a
fiction. The duration budget has no such interaction: the waits count *towards*
it, and only a run that reaches `HealthyRuntime` clears it.

## Request body limits on Connect mounts

`APIServer` no longer wraps the request body of a Connect subtree in an
`http.MaxBytesReader`; a Connect request is bounded per message by the new
`ServiceOptions.MaxMessageBytes` instead. The reader counted bytes over the
life of the request, and a client or bidirectional stream's request body *is*
the stream, so such a stream died once its cumulative traffic passed
`DefaultMaxBodyBytes` — 8 MiB once, not per message.

**A service that raised `APIServerMaxBodyBytes` for the sake of a large
Connect request sets `MaxMessageBytes` to the same number**, since that is now
what bounds it:

```go
// Before: the listener limit was what let a large Connect request through.
server := elephantine.NewAPIServer(logger, addr,
	elephantine.APIServerMaxBodyBytes(32<<20))

// After: the listener limit still covers Twirp and every mount the service
// makes itself, and MaxMessageBytes covers the Connect subtree.
opts.MaxMessageBytes = 32 << 20
```

Nothing else needs a change:

- A unary call is one message, so a unary request is bounded exactly as it was.
- A zero `MaxMessageBytes` is `DefaultMaxBodyBytes`, not connect-go's "any
  size", so a service that composes its options by hand is bounded too. A
  negative value asks for no limit.
- Every non-Connect mount keeps the stream-level limit, and the cheap `413`
  for a request that *declares* an oversized `Content-Length` fires on every
  path as before.

Responses are unaffected. The new `ServiceOptions.MaxSendMessageBytes` bounds
what a Connect handler may answer with, and is off unless set — connect-go
checks it against the compressed wire size, so defaulting it on would refuse
the same call for one caller and serve it to another.

[Message size limits](../connect.md#message-size-limits) in `docs/connect.md`
has the full reasoning, including why a Connect request body is deliberately
not bounded in total any more.
