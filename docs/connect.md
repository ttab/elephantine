# Connect in the elephant fleet

How an elephant service serves, calls, tests and generates Connect, and how it
keeps serving Twirp next to it for as long as it has Twirp callers. This is the
working reference for engineers and agents. The decisions behind it are recorded
in `CONNECT_MIGRATION.md` in the elephant-repository repository, which is the
master plan; the step-by-step instructions for moving a service or a client are
in [migration-service.md](migration-service.md) and
[migration-client.md](migration-client.md).

## The shape

A service implements the plain protobuf interface once:

```go
Get(ctx context.Context, req *repository.GetDocumentRequest) (*repository.GetDocumentResponse, error)
```

That is the interface `protoc-gen-twirp` has always generated, and it stays the
contract. Connect and Twirp are two generated adapters around it:

- The Twirp mount is the generated `New<Service>Server`, unchanged, with one
  interceptor (`rpc.TwirpInterceptor()`) that turns the Connect errors the
  handlers return into Twirp errors on the way out.
- The Connect mount is `New<Service>ServiceHandler` from the `<pkg>connect`
  package, generated by `protoc-gen-elephant-rpc`, which unwraps
  `connect.Request` and wraps `connect.Response` around the plain interface.

Handlers never see a `connect.Request`. Request headers are handled by HTTP
middleware in front of both mounts, and the interceptors read what the
middleware put on the context. The only thing in a handler that knows about
the protocol is the error it returns, and that is `*connect.Error` built
through the `rpc` package on both stacks.

Retiring Twirp from a service is therefore a deletion: the mount line, the
interceptor and the Twirp test client. Nothing in the handlers changes.

## Paths, protocols and wire formats

| | Twirp | Connect |
|---|---|---|
| Path | `POST /twirp/<pkg>.<Service>/<Method>` | `POST /<pkg>.<Service>/<Method>` |
| Content types | `application/protobuf`, `application/json` | `application/proto`, `application/json`, plus gRPC and gRPC-Web selected by content type |
| Request headers | `Authorization` | `Authorization`; clients also send `Connect-Protocol-Version: 1` and may send `Connect-Timeout-Ms`, neither required by the server |
| Error body | `{"code":"not_found","msg":"…","meta":{"k":"v"}}` | `{"code":"not_found","message":"…","details":[{"type":"elephantine.rpc.ErrorMeta","value":"<base64>"}]}` |
| JSON defaults | omitted (`WithServerJSONSkipDefaults`) | omitted (protojson default) |

The paths never overlap, so one server mounts both. Connect at the standard
root, no prefix (decision 2 in the master plan): every Connect client and proxy
assumes it, and the generated `Procedure` constants say so. An ingress rule that
routes on `/twirp/` needs a sibling rule for the unprefixed paths.

`Connect-Timeout-Ms` becomes the handler's context deadline. A plain `curl`
with `Content-Type: application/json` against the Connect path works without
any Connect header.

### Error codes and HTTP status

The 16 codes are shared and spelled identically (`not_found`,
`failed_precondition`, ...). Twirp's `malformed` and `bad_route` are
framework-generated and map to `invalid_argument` and `unimplemented` when
translated. The HTTP status is identical except:

| Code | Twirp | Connect |
|---|---|---|
| `canceled` | 408 | 499 |
| `deadline_exceeded` | 408 | 504 |
| `failed_precondition` | 412 | 400 |

`failed_precondition` is the one that matters: document locks, system locks
and workflow rules return it. Nothing should key on the status; read the code
from the body, or from `rpc_protocol_responses_total{code=…}` in metrics.
`rpc.HTTPStatus(code)` is the Connect mapping if a service needs it.

### Error metadata

Connect has no free-form meta map in the body, and its `Error.Meta()` renders
as HTTP headers, which our underscored keys (`lock_holder_sub`,
`required_any_of_scopes`, `argument`) and nginx's default of dropping
underscored headers make unusable. Metadata therefore travels as one typed
error detail, `elephantine.rpc.ErrorMeta` (`rpc/errormeta.proto`), and the
Twirp translation flattens it back into Twirp's `meta` map. Go callers read it
with `rpc.Meta(err)`; other Connect clients with their runtime's `findDetails`.
The message is byte for byte the same on both stacks.

Richer typed details are a design surface for after the transition: the Twirp
adapter can only render `ErrorMeta`, so anything else would break parity while
both stacks are mounted.

## Serving

### With `elephantine.APIServer`

```go
opt, err := elephantine.NewDefaultServiceOptions(
    logger, authParser, reg, elephantine.ServiceAuthRequired)
if err != nil {
    return fmt.Errorf("set up service options: %w", err)
}

// Twirp: unchanged, and ServerOptions() now installs rpc.TwirpInterceptor.
server.RegisterAPI(repository.NewDocumentsServer(svc, opt.ServerOptions()), opt)

// Connect: the generated constructor returns the mount path and the handler.
path, handler := repositoryconnect.NewDocumentsServiceHandler(
    svc, opt.HandlerOptions()...)
server.RegisterConnect(path, handler, opt)
```

`NewDefaultServiceOptions` fills in both sides: the Twirp hooks and the Connect
interceptors for logging, metrics and authentication, so the two mounts behave
identically by construction. `ServiceOptions.Interceptors` is the Connect
chain, `HandlerOptions()` turns it into `connect.HandlerOption`s.

The plaintext listener serves HTTP/1.1 and HTTP/2 side by side (Go's
`http.Protocols` with unencrypted HTTP/2 on), which is what makes gRPC
reachable without TLS. Twirp, SSE and websocket callers are unaffected. An
ingress in front of the service still has to allow HTTP/2 to the backend before
an external gRPC caller can reach it.

### With your own router

A service that mounts its RPCs on its own router (elephant-repository uses
`httprouter`) does the same thing by hand: the Connect constructor returns the
service root (`/elephant.repository.Documents/`) and a handler, so mount it as
a catch-all under that root, `POST` only, behind the same authentication
middleware as the Twirp routes. Build the interceptor chain once and give it to
every Connect mount:

```go
metrics, err := rpc.MetricsInterceptor(reg)          // shares collectors with the Twirp hooks
interceptors := []connect.Interceptor{
    metrics,
    rpc.LoggingInterceptor(logger),
    // rpc.LegacyTwirpErrors(),  only while handlers still return twirp errors
}
handlerOpts := []connect.HandlerOption{connect.WithInterceptors(interceptors...)}
```

Interceptors apply outermost first. Put the error-coding interceptors innermost
so logging and metrics see the code the caller will be answered with.

### Errors in handlers

Handlers return `*connect.Error` through the `rpc` helpers and never import
`twitchtv/twirp`:

| Twirp | `rpc` |
|---|---|
| `twirp.NewErrorf(code, …)` | `rpc.Errorf(code, …)` |
| `twirp.InvalidArgumentError(arg, msg)` | `rpc.InvalidArgument(arg, msg)` |
| `elephantine.InvalidArgumentf(arg, …)` | `rpc.InvalidArgumentf(arg, …)` |
| `twirp.RequiredArgumentError(arg)` | `rpc.RequiredArgument(arg)` |
| `twirp.NotFoundError(msg)` | `rpc.NotFound(msg)` |
| `twirp.InternalErrorf(…)` / `twirp.Internal.Errorf(…)` | `rpc.Internalf(…)` |
| `twirp.FailedPrecondition.Errorf(…)` | `rpc.FailedPreconditionf(…)` |
| `twirp.PermissionDenied.Errorf(…)` | `rpc.PermissionDeniedf(…)` |
| `twirp.Unauthenticated.Error(msg)` | `rpc.Unauthenticated(msg)` |
| `twirp.AlreadyExists.Error(msg)` | `rpc.AlreadyExists(msg)` |
| `err.WithMeta(k, v)` | `rpc.WithMeta(err, k, v)` |
| `err.MetaMap()` | `rpc.Meta(err)` |
| `elephantine.IsTwirpErrorCode(err, code)` | `rpc.IsCode(err, connect.Code…)` |
| `elephantine.RequireAnyScope(ctx, …)` | `rpc.RequireAnyScope(ctx, …)` |
| `string(twirp.<Code>)` | `connect.Code<X>.String()` (same strings) |

Rules that follow from the shape:

- **Never wrap an RPC error.** `fmt.Errorf("get document: %w", rpc.NotFound(…))`
  turns a coded error into an uncoded one. Return the helper's result as it is.
- **An uncoded error is `internal` on Twirp and `unknown` on Connect** unless
  the service says otherwise. A service that still has bare `fmt.Errorf`
  returns in its handlers adds an innermost interceptor that gives uncoded
  errors `connect.CodeInternal` (elephant-repository's `codeUncodedErrors`),
  or removes the bare returns. Either way, document which.
- **Every RPC checks its scope explicitly** with `rpc.RequireAnyScope`.
  Authentication is middleware and knows nothing about scopes; a handler
  without a scope check fails open on both stacks.
- `rpc.RequireAnyScope` returns `unauthenticated` for an anonymous caller and
  `permission_denied` with `required_any_of_scopes` meta otherwise, exactly as
  the root helper did.

### Authentication

`ServiceOptions.SetAuthInfoValidation` is protocol-neutral HTTP middleware. It
parses `Authorization`, puts the `AuthInfo` on the request context, and a
request it could not authenticate is let through with the reason recorded, which
the Twirp hook and the Connect interceptor turn into the coded error before the
handler runs: `unauthenticated` for a missing authorization, `permission_denied`
for an invalid one. `ServiceAuthOptional` lets a missing authorization through;
an invalid one always fails. Handlers read `elephantine.GetAuthInfo(ctx)` (or
`rpc.GetAuthInfo`, the same function) on both stacks.

### Metrics

`rpc_requests_total`, `rpc_duration_seconds` and `rpc_responses_total` keep
their names, labels and label values on both stacks, and the collectors are
shared, so a dual-stack server registers each once. `service` is the short
service name (`Documents`), `method` the RPC name, `status` the HTTP status
actually sent (so 400 for `failed_precondition` on Connect, 412 on Twirp).

`rpc_protocol_responses_total{service,method,protocol,code}` is new and
reported by both stacks. `protocol` is `twirp`, `connect`, `grpc` or `grpc-web`;
`code` is the RPC code or `ok`. Filter on `protocol="twirp"` to see which
methods still have Twirp callers; filter on `code` for the error breakdown the
status label cannot give. See [metrics.md](metrics.md#rpc-metrics).

### CORS

Browser Connect clients send `Connect-Protocol-Version` and
`Connect-Timeout-Ms` on every call. `elephantine.CORSOptions` allows them by
default; a service that replaced `AllowedHeaders` outright adds them itself.

## Calling

### Go

```go
docs := repositoryconnect.NewDocumentsServiceClient(httpClient, baseURL)
```

returns the plain `repository.Documents` interface, so it is a drop-in for
`repository.NewDocumentsProtobufClient`. `httpClient` carries the bearer token
the way it always has (an `oauth2` client, or `elephantine.NewHTTPClient` with
`WithTokenSource`); `baseURL` is the server root, not a per-service path.

Per-call headers, which `twirp.WithHTTPRequestHeaders` provided, are a context
value and one client interceptor:

```go
docs := repositoryconnect.NewDocumentsServiceClient(httpClient, baseURL,
    connect.WithInterceptors(rpc.PropagateHeaders()))

ctx = rpc.WithOutgoingHeaders(ctx, http.Header{"X-Forwarded-For": {addr}})
```

Error checks use `rpc.IsCode(err, connect.CodeNotFound)`, which recognises both
error types, so a caller can move its checks before or after its constructor.
Metadata is `rpc.Meta(err)`.

The connect-go generated `New<Service>Client`, which speaks in
`*connect.Request[T]`, is generated too and is the right client when a call
needs response headers or trailers. The `Service` infix tells the adapters from
connect-go's own constructors.

### Other languages

Connect has runtimes for TypeScript (`@connectrpc/connect-web`), Swift, Kotlin
and others, all generating from the `.proto` file. For JSON over `fetch` or
`curl`:

```
POST /elephant.repository.Documents/Get
Content-Type: application/json
Authorization: Bearer …

{"uuid": "…"}
```

On error the body is `{"code","message","details"}`; `ErrorMeta` is the detail
of type `elephantine.rpc.ErrorMeta`, and the Connect JSON encoding includes a
`debug` rendering of it next to the base64 `value`.

## Testing

- `test.IsRPCError(t, err, connect.CodeNotFound)` asserts a code and accepts a
  Twirp or a Connect error.
- `test.ErrorParity(t, twirpErr, connectErr)` asserts that the same call
  answered both stacks with the same code, message and metadata. This is the
  acceptance test for a service's error flip.
- Run the API test suite against both stacks. The cheap pattern, used by
  elephant-repository, is one switch for the whole suite: an environment
  variable (`TEST_RPC_STACK=twirp|connect`) chooses which client constructors
  the test context builds, a per-test override exists for the parity tests, and
  CI runs the suite twice. Both mounts are always up; the switch only decides
  which one the clients talk to.
- Pin the wire shape of a couple of error bodies with golden files on both
  stacks, so a change in either encoding is a visible diff.
- The elephantine `rpc` package's own tests are the reference for asserting
  metric label parity across stacks (`testutil.GatherAndCompare` against a
  fixture service mounted both ways).

## Generating

Generation is the `rpc` namespace of `github.com/ttab/mage`: `mage rpc:generate`
runs buf and every plugin as `go run <module>@<version>` at versions pinned in
that package. No docker, nothing installed, no `buf.gen.yaml` in the
repository. Per service it writes `service.pb.go`,
`<pkg>connect/service.connect.go` (connect-go), `<pkg>connect/service.elephant.go`
(the adapters), `service.twirp.go` when `rpc.Twirp = true`, and
`service.rpc.go` (the plain interface) when Twirp is off. Nothing else: the
OpenAPI specifications are gone (decision 8).

A repository that imports a `.proto` from another module vendors it with
`mage rpc:vendorProto <module> <file>`; the only case in the fleet is
`newsdoc/newsdoc.proto` from elephant-api. The target is idempotent, so CI can
run it and `git diff --exit-code` reports drift.

`protoc-gen-elephant-rpc` lives in this repository under `cmd/`. Until
`ttab/mage` pins a released version of it, generation needs
`ELEPHANT_RPC_PLUGIN=<path to an elephantine checkout>` or the adapters are
silently left as they were. See the [README](../README.md#generating-the-rpc-adapters)
for the plugin's options.

The generated code imports only `connectrpc.com/connect`, `context`,
`net/http` and the message package. It never imports elephantine, which is what
keeps elephant-api free of elephantine's dependencies. The dependency runs the
other way: services import both.

## A new service

A new service is Connect-only. There is no Twirp mount, no `rpc.Twirp`, and no
`twitchtv/twirp` anywhere in the module:

1. Declare the service in `rpc/<name>/service.proto` (`mage rpc:stub` scaffolds
   one) and run `mage rpc:generate`. The plain interface comes out in
   `service.rpc.go`, the adapters in `<pkg>connect/`.
2. Implement the interface; return errors through `rpc`; check scopes with
   `rpc.RequireAnyScope` in every method.
3. Mount with `NewDefaultServiceOptions` and `RegisterConnect`, as above.
4. Test with the Connect client adapter and `test.IsRPCError`.
5. Document the paths as `/<pkg>.<Service>/<Method>` and the error body as
   Connect's; nothing about `/twirp/` belongs in a new service's documentation.
